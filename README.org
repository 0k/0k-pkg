* Overview

~0k-pkg~ is a shell-based package management and release automation
toolkit. It provides a unified interface for building, testing, and
publishing packages across multiple ecosystems (Rust/Cargo,
Python/Hatch, TypeScript, JavaScript/npm, and shell packages).

The toolkit auto-detects the package type from project files and
routes commands to the appropriate handler, enabling consistent
workflows regardless of the underlying technology.

* Features

- Automatic package type detection based on project files
- Unified command interface across different package ecosystems
- Safe testing using unionfs-fuse overlays (source remains unmodified)
- Multiple source selection modes: committed, workdir, staged, intermediate commits
- Caching of test results and build artifacts
- Coverage report aggregation
- Integration with ~dovis~ for cross-platform testing
- Extensible architecture for adding new package types
- Explicit, opt-in release announcement previews and Matrix delivery

* Supported Package Types

| Type       | Detection            | Build / publish        | Extra checks and scripts                 |
|------------+----------------------+------------------------+------------------------------------------|
| all        | always               | (drives the pipeline)  | license, debugger, merge markers, ~YYY~, vendored scripts; git hooks |
| autogen    | ~autogen.sh~         | -                      | package-name check; ~90-prepare.sh~      |
| cargo      | ~Cargo.toml~         | crate → crates.io      | docs.rs check; clippy/fmt/doc/org lint; ~20-org-to-md.sh~ |
| hatch      | ~pyproject.toml~ with ~hatchling~ + ~hatch-vcs~ | wheel, sdist → PyPI | pdb/rst checks; ~25-changelog.sh~ |
| python     | ~setup.py~           | wheel, sdist → PyPI    | pdb/rst checks; flake8 lint; ~25-changelog.sh~ |
| npm        | ~package.json~       | npm pack → npm         | transpile check                          |
| ts         | ~tsconfig.json~      | npm pack → npm         | transpile check; ~20-org-to-md.sh~       |
| kal-sh     | ~pkg/~ + ~test/test~ | deb                    | -                                        |
| charm      | ~metadata.yml~       | -                      | -                                        |

The ~pkg~, ~lint~, ~vendor~ and ~pkg-git-hook~ verbs are implemented
once, by ~all~; the per-type directories only contribute hook
scripts.  ~t~ (tests) is implemented per type.

* Installation

Ensure dependencies are installed:

#+begin_src sh
# Core dependency
apt install unionfs-fuse

# For release-pipeline YAML config parsing (Rust implementation, not the legacy PyPI one)
cargo install shyaml-rs

# For announcements (Mike Farah yq v4, pandoc for Markdown, plus Python 3 stdlib)
# Install yq using your platform's package/install method.
yq --version
pandoc --version

# Per-language dependencies
cargo install toml-cli   # For Cargo/Hatch packages
apt install jq           # For npm/Hatch packages
#+end_src

Install ~0k-pkg~ itself.  Nothing is copied: the clone is the
installation, and everything else is a symlink into it, so a
~git pull~ is an upgrade.

#+begin_src sh
# bash-shlib must be available (provides /etc/shlib)
# dovis must be installed for testing

git clone https://github.com/0k/0k-pkg.git ~/dev/sh/0k-pkg   # or wherever you keep sources
#+end_src

Point ~pkgcmd~ at the plugin tree.  ~pkgcmd~ loads its package types
from ~\~/.pkgcmd.d/~; without this symlink no command is found:

#+begin_src sh
ln -s ~/dev/sh/0k-pkg/src/etc/pkgcmd.d ~/.pkgcmd.d
#+end_src

Expose the commands on your ~PATH~.  ~pkgcmd~ dispatches on the
name it was invoked by (~${0##*/}~), so each verb is a symlink
named after it, placed in a directory that is already on ~PATH~:

#+begin_src sh
ln -s ~/dev/sh/0k-pkg/src/bin/pkgcmd ~/.local/bin/pkgcmd
for verb in pkg t lint pkg-git-hook; do
    ln -s pkgcmd ~/.local/bin/$verb
done
#+end_src

(~vendor~ is reached as ~pkg vendor~.)

* Usage

** Main Commands

*** ~pkg~ (alias for ~pkg-common~)

The primary release workflow command. Runs sanity checks, tests,
builds distribution files, validates them, and optionally publishes.

#+begin_src sh
# Run full release workflow on committed code (default)
pkg

# Run on working directory state
pkg -w

# Run on staged changes only
pkg --staged

# Test all intermediate commits since last push
pkg -i

# Publish after successful validation
pkg --publish

# Skip tests (for quick iteration)
pkg --no-tests

# Skip distribution building
pkg --no-dist
#+end_src

*** ~pkg vendor~ - Ship build scripts with the project

A fresh ~git clone~ of a project must be buildable without 0k-pkg
installed: only ~git~, ~sed~, ~date~ and ~grep~ should be needed to
run ~./autogen.sh~ and then the language's own build tool.  The
autotools model is followed: 0k-pkg plays the role of ~autoreconf~
(private, developer-side), and ~autogen.sh~ plus
~.package.d/autogen.d/*~ play the role of ~configure~ (public,
committed, self-sufficient).

#+begin_src sh
pkg vendor           # copy canonical autogen.sh + plugin autogen.d/ scripts
pkg vendor --dry-run # report what would change
#+end_src

What gets copied depends on the package types that apply to the
project (see each plugin's ~autogen.d/~ directory):

| Plugin    | Script                | Purpose                                              |
|-----------+-----------------------+------------------------------------------------------|
| ~autogen~ | ~90-prepare.sh~       | ~%%version%%~ substitution in ~$FILES~                |
| ~cargo~   | ~20-org-to-md.sh~     | ~README.org~ → ~README.md~ (pandoc) + changelog appended, since crates.io only renders the README |
| ~hatch~   | ~25-changelog.sh~     | ~CHANGELOG.rst~ from git history (gitchangelog)       |
| ~python~  | ~25-changelog.sh~     | idem                                                  |
| ~ts~      | ~20-org-to-md.sh~     | ~README.org~ → ~README.md~ (pandoc) + changelog appended, since npmjs.com only renders the README |

Provenance is written to ~.package.d/autogen.d/MANIFEST~ (source
commit and a sha256 per file).  Commit the vendored files together
with the manifest.

To keep a local modification of a vendored script, add the line
~## pkgcmd: local-override~ within its first five lines; ~pkg vendor~
then leaves it alone.  Scripts that no longer exist upstream are
removed on the next ~pkg vendor~ unless modified or overridden.

At release time ~all/source/check/vendored~ verifies that every
vendored file matches its manifest entry (error on drift without
the override marker, error on a project script silently shadowing a
plugin one), and warns when 0k-pkg now ships a newer copy: run
~pkg vendor~, re-test, commit.

Optional tools used by vendored scripts (~pandoc~, ~gitchangelog~)
are checked with ~depends_soft~: missing, the step is skipped with a
warning so that ~./autogen.sh~ still succeeds for someone who only
wants to build.  ~pkg~ exports ~AUTOGEN_STRICT=1~ for the whole
release pipeline, which turns those into hard errors.

*** ~pkg announce~ - Preview and send opt-in release and commit announcements

Announcements are a separate, explicit workflow.  ~pkg --publish~ never
checks, previews, or sends announcements.  A project opts in only by adding
~.package.d/announcements.yaml~.

#+begin_src sh
# Read-only readiness for every configured target
pkg announce check

# Read-only readiness plus an exact preview and approval digest
pkg announce check --target community --draft /tmp/release.txt --release 1.2.3

# Read context for drafting (verified receipt when available, otherwise
# one bounded page explicitly marked untrusted)
pkg announce context --target community

# Send the exact file/version/destination approved in the preview
pkg announce send --target community --message /tmp/release.txt \
  --release 1.2.3 --approved-sha256 DIGEST_FROM_CHECK

# Correct a release's announcement in place (Matrix edit), same two steps
pkg announce check --target community --draft /tmp/fixed.txt --release 1.2.3 --replace
pkg announce send --target community --message /tmp/fixed.txt \
  --release 1.2.3 --approved-sha256 DIGEST_FROM_CHECK --replace

# Projects that publish without release tags announce a commit instead:
# --commit replaces --release in check and send (with or without --replace)
pkg announce check --target community --draft /tmp/fix.txt --commit 1a0a48a
pkg announce send --target community --message /tmp/fix.txt \
  --commit 1a0a48a --approved-sha256 DIGEST_FROM_CHECK
#+end_src

The subject of an announcement is either a release tag (~--release~) or a
commit (~--commit~); the two are mutually exclusive.  A commit may be given
abbreviated or by any revision name: it is resolved once to its full hash,
and that hash is what the preview shows, the digest binds, and the receipt
records.  A commit announcement's identity simply has no ~release~ field, so
an approval for a release can never send as a commit announcement, nor the
reverse.  Receipts are kept per subject: announcing the same commit again
returns its existing receipt, and ~--replace~ edits that commit's
announcement.

All successful commands write JSON data to stdout.  Diagnostics and errors
go to stderr.  ~check~ and ~context~ use Matrix GET requests only.  Supplying
~--draft~ to ~check~ does not write a receipt and cannot send a message.

The draft is Markdown.  It is sent as Matrix ~m.text~ with the Markdown
source as ~body~ (what clients without HTML support display) and its
~pandoc~ rendering as ~formatted_body~ (~format: org.matrix.custom.html~).
Pandoc runs in ~--sandbox~ mode with raw HTML, raw TeX and raw attributes
disabled, so markup typed in the draft is escaped rather than injected;
single newlines are kept as line breaks and bare URLs become links.  A
missing or failing ~pandoc~ aborts before anything is sent.

The preview displays the full message body and the exact Matrix content
(including the rendered HTML), sender, configured alias, resolved room ID,
release tag, full dereferenced commit, digest version, and approval digest.
The versioned digest binds those values to the stable project identifier
(canonical ~origin~ URL when available, otherwise the documented
~local:/absolute/repository/path~ fallback), normalized homeserver,
target/transport, the exact UTF-8 file bytes, and the exact content sent, so
a change in the rendered HTML also invalidates approval.  No newline or
whitespace normalization is applied.  Moving a tag, editing the file,
retargeting an alias, changing sender, or changing homeserver invalidates
approval.  Receipts written before HTML rendering existed (plain ~m.text~
content) remain valid.

~--replace~ edits the release's existing announcement instead of posting a
second one: the content is a Matrix ~m.replace~ edit of the original
announcement event (clients show the new text in place of the old one).
It requires a verified completed announcement for that release, and every
edit targets the original event, never a previous edit.  The edited event is
part of the approval digest, so a preview made without ~--replace~ cannot
authorize an edit.  Each edit is its own durable, retry-safe operation with
its own receipt; the original announcement's receipt is never modified.

Before sending, the command verifies the credential's exact Matrix user,
alias resolution, joined membership, effective ~m.room.message~ power level,
and that the room is unencrypted.  It never joins, renames, logs in, or
obtains admin credentials.  Redirects are not followed, so an authorization
header cannot cross hosts.

Sending is durable and retry-safe.  Private evidence under
~$XDG_STATE_HOME/pkg/announcements/~ records a stable random Matrix
transaction ID, token SHA-256 fingerprint (never the token), approved digest,
identity, and content before the PUT.  A returned event ID is persisted before
GET verification.  Unknown outcomes remain pending; retry uses the same
transaction ID.  A changed credential, destination, content, commit, or
malformed/tampered evidence fails closed.  A completed operation returns its
existing receipt without another PUT after read-only remote verification, even
when a stale pending file remains or the valid sender token has rotated.
Completed receipts include the verified event permalink, Matrix
~origin_server_ts~, and an ISO UTC posting time.

*** ~pkg-git-hook~ - Global git hooks

Runs the git hook check scripts for a given hook name.  This is the
entry point used by the global ~core.hooksPath~ trampolines (see the
~git~ charm in =0k-cfg=): each trampoline is a two-line script that
~exec~s ~pkg-git-hook <HOOK> "$@"~.

#+begin_src sh
# Called by git through ~/.config/git/hooks/pre-commit
pkg-git-hook pre-commit

# Called by git through ~/.config/git/hooks/commit-msg
pkg-git-hook commit-msg .git/COMMIT_EDITMSG
#+end_src

For a hook ~HOOK~, every executable in ~git-hook/HOOK/~ of each
applying package type is run in sorted order with the arguments git
passed to the hook.  The first non-zero exit aborts and becomes the
hook's exit code.  On success the repository-local
~.git/hooks/HOOK~ is ~exec~'d if present, so per-repository hooks
keep working underneath the global ones.

The command is silent on success, as git hooks are expected to be.

It is not named ~git-hook~: git prepends its ~--exec-path~ to ~PATH~
when running hooks, and ~git-core/git-hook~ (the ~git hook~
builtin) would shadow it.

Checks shipped for the ~all~ package type:

| Hook         | Script                | Purpose                                                        |
|--------------+-----------------------+----------------------------------------------------------------|
| ~pre-commit~ | ~10-readme-md~        | Block ~README.md~ when ~README.org~ exists                     |
| ~pre-commit~ | ~20-opencode-paths~   | OpenCode sessions: block ~doc/admin.org~, ~.sisyphus/~, ~*.md~ |
| ~pre-commit~ | ~30-org-clock~        | ~org-cli clock check~ on staged ~*.org~                        |
| ~pre-commit~ | ~50-cargo-path-deps~  | Block new Cargo ~path~ dependencies leaving the repository     |
| ~commit-msg~ | ~10-opencode-msg~     | OpenCode sessions: block ~Co-authored-by~ / "Ultraworked"      |
| ~commit-msg~ | ~20-convention~       | Commit message convention audit                                |
| ~commit-msg~ | ~90-assisted-by~      | Add ~Assisted-by:~ trailer from ~ai-audit~                     |

~50-cargo-path-deps~ refuses a commit whose staged ~Cargo.toml~ (at any
depth) adds a dependency, or a ~[patch.*]~ entry, whose ~path~ resolves
outside the repository (~foo = { path = "../foo" }~), and a staged
~Cargo.lock~ that turns a crate locked from a registry or git at
~HEAD~ into a local path package.  Path dependencies already committed
and paths inside the repository (workspace members) are accepted.
Keep such a line uncommitted, or use a git-ignored ~[patch.crates-io]~,
to build against a local checkout.  It needs ~python3~ >= 3.11 (or
~tomli~), only when a Cargo file is staged.

~20-convention~ requires the first word of a title's description to
be an imperative verb listed in ~git-hook/commit-msg/verbs.txt~ (one
base form per line, British and American spellings both accepted).
When an inflected form is used (~added~, ~using~), it names the base
verb to write instead, looked up in ~verb-forms.tsv~ (UniMorph
English, CC BY-SA 3.0).  A genuine base-form verb that is not listed
yet is rejected with an instruction to ask the user before adding it
to ~verbs.txt~; words reviewed and refused live in ~not-verbs.txt~
and are reported as "not a verb".

~20-convention~ also requires the body to be wrapped at 80 columns,
counted in characters.  Trailers (~Refs: …~) and lines indented by 4
spaces or a tab (code, quoted output) are not checked.  A line whose
last token is longer than 80 on its own, like a long URL in
double-backticks, cannot be rewrapped: it is kept with a warning.
To keep another long line on purpose, commit with
~COMMIT_MSG_ALLOW_LONG_LINES=1~: body-width rejections become
warnings, every other rule still applies.  LLM agents must get the
user's approval before setting it.

~90-assisted-by~ writes the ~Assisted-by:~ trailers given by
~ai-audit session assisted-by~ for the committing AI session.  When
other models authored the content, ~COMMIT_ASSISTED_BY~ names them
instead (comma-separated ~Agent:model~, e.g.
~COMMIT_ASSISTED_BY='Claude:claude-sonnet-4-5' git commit …~): it
replaces session detection, and a malformed value rejects the commit.
LLM agents must confirm with the user before setting it.

The ~*-opencode-*~ hooks only act when the ~$OPENCODE~ environment
variable is ~1~ (set by the OpenCode agent harness) and are inert
otherwise.  ~30-org-clock~ needs ~org-cli~ and ~90-assisted-by~
needs ~ai-audit~; both hooks skip silently when the tool is absent.

* Configuration

** User Configuration

Global configuration is stored in:

- ~\~/.config/pkg/main.yml~ - Main configuration file (YAML format)
- ~\~/.pkgcmd.d/~ - Package types and their hook scripts.  Normally
  a symlink to the clone's ~src/etc/pkgcmd.d~ (see Installation);
  a real directory holding your own ~<type>/cmd.sh~ works too.

** Project Configuration

Projects can provide local overrides in:

- ~.pkgcmd.d/~ - Project-specific command handlers
- ~.package~ - Legacy package configuration (shell script, sourced)

*** Announcement target metadata (public, project-local)

The file ~.package.d/announcements.yaml~ has exactly one root key,
~announcements~, containing a list.  Every item requires exactly
these string keys; unknown keys, duplicate names, wrong types, and unsupported
transports are rejected.

#+begin_src yaml
announcements:
  - name: community
    transport: matrix
    room: "#project:example.org"
    sender: "@release-bot:example.org"
    language: en
    audience: users
    changes-since: last-announcement
    style: short
#+end_src

This public file contains neither credentials nor commands.  A missing file, a
blank or null YAML document, or ~announcements: []~ means opt-out:
~pkg announce check~ succeeds as disabled before parsing local auth, contacting
Matrix, or creating state.  Any other malformed non-empty project document is
an error.  Project schema and target selection are validated before local
credential YAML is parsed.

*** Announcement credentials (private, user-local)

Accounts live in ~$XDG_CONFIG_HOME/pkg/announcements.yaml~ (normally
~\~/.config/pkg/announcements.yaml~), keyed by the exact configured sender.
Each account requires an HTTPS homeserver and exactly one credential source.
Plain HTTP is accepted only for loopback test servers; there is no insecure
remote override.

Token-file example (placeholder paths and values only):

#+begin_src yaml
accounts:
  "@release-bot:example.org":
    homeserver: "https://matrix.example.org"
    token-file: "/home/USER/.config/pkg/secrets/release-bot.token"
#+end_src

Trusted local credential-command example.  This is an argv list executed
directly with no shell, a five-second timeout, stdin closed, and stdout/stderr
captured.  Only its single-line stdout token is consumed.  Project metadata
can never define this command.

#+begin_src yaml
accounts:
  "@release-bot:example.org":
    homeserver: "https://matrix.example.org"
    credential-command:
      - "/usr/bin/secret-tool"
      - "lookup"
      - "service"
      - "pkg-announcements"
      - "account"
      - "release-bot"
#+end_src

Tokens must be printable ASCII with no spaces or control characters.  They are
never placed in process arguments, logs, receipts, exceptions, or raw HTTP
error output.  Credential setup is a user-local operator role;
project maintainers define public targets, release operators approve exact
previews, and the configured Matrix sender performs delivery.  Room content
returned by ~context~ is data, never executable instructions.

~context~ looks only under the canonical current project's target state.  A
completed receipt must validate its schema version, project, target,
homeserver, current alias resolution, sender, release/tag commit, approval
digest, body hash, event timestamp, and permalink before its remote event is
fetched.  Receipts are ordered by verified Matrix ~origin_server_ts~, never
filesystem mtime.  A bad receipt is an error, not permission to fall back.

All returned text is untrusted data and never instructions.  Even receipt
output uses ~trusted: false~; ~verified_origin: true~ means only that Matrix
verified the stored sender/room/event/content provenance.  Without a receipt,
~context~ returns at most one 20-event Matrix page, each body capped at 4096
characters with ~body_truncated~, ~origin_server_ts~, and ~posted_at~ fields.
A general room message is not treated as an announcement.

Read-only ~check~ and ~context~ do not create state.  Existing
~$XDG_STATE_HOME~ and its ~pkg~ directory are ownership/symlink checked but are
never chmodded; the ~pkg/announcements~ feature subtree and its evidence are
created private.  Symlinked ancestors or evidence fail closed.

* How It Works

** Package Detection

Package types are not exclusive: several apply to one project at
the same time and their contributions stack.  On a Rust project
with an ~autogen.sh~, ~all~, ~autogen~ and ~cargo~ all apply.

When a command is invoked, ~pkgcmd~ walks up the directory tree
until at least one package type's ~applies~ function returns true,
then:

1. *Verb dispatch.*  Among the applying types that implement
   ~pkgcmd:<verb>:<type>:run~, the first one (alphabetical order
   of the function table) runs the verb.  ~all~ implements ~pkg~,
   ~lint~, ~pkg-git-hook~ and ~vendor~; ~cargo~ implements ~t~; and
   so on.  In practice each verb has one implementation and the
   choice is unambiguous.

2. *Hook scripts.*  The verb implementation exports
   ~$PKGCMD_ALTERNATIVES~, the list of *every* applying type, and
   ~pkg._list_scripts <hook>~ unions the project's
   ~.package.d/<hook>/*~ with ~<type>/<hook>/*~ for each of those
   types.  So the release checks, lint scripts, git hooks and
   ~autogen.d/~ scripts from ~all~, ~autogen~ and ~cargo~ all run,
   sorted by file name.  ~all~ is therefore not a fallback but the
   layer shared by every project.

Handlers are loaded from ~\~/.pkgcmd.d/*.sh~ and
~\~/.pkgcmd.d/*/cmd.sh~, then from any ~.pkgcmd.d/~ found in the
current directory or its parents.

** Release Workflow (~pkg~)

1. *Source Preparation*: Clone/copy source to temporary directory
   based on selected source mode
2. *Sanity Checks*: Run scripts from ~source/check/~ (license,
   debugger statements, merge markers, vendored scripts in sync)
3. *Tests*: Execute via ~dovis~ across configured platforms
4. *Coverage*: Aggregate coverage reports if enabled
5. *Dist Checks*: Run scripts from ~dist/check/~
6. *Build*: Execute scripts from ~release/build/~ (wheel, sdist, npm
   pack, etc.)
7. *Release Checks*: Validate built artifacts via ~release/check/~
8. *Publish*: If ~--publish~, execute scripts from ~release/publish/~

** Safe Testing with Overlays

~pkg~ uses ~unionfs-fuse~ to create copy-on-write overlays. Tests run
in an isolated environment where:

- The original source remains untouched
- Modifications are written to a temporary upper layer
- Each test run starts from a clean state

Build artifacts are placed in ~/tmp~ by default.

* Extending

To add support for a new package type, create a handler in
~\~/.pkgcmd.d/<type>/cmd.sh~ or ~\~/.pkgcmd.d/<type>.sh~:

#+begin_src sh
# Detection function - return 0 if this type applies
pkgcmd:<type>:applies() {
    [ -e "marker-file" ]
}

# Optional: mark as base type for inheritance
pkgcmd:<type>:is_base() {
    [ -e "marker-file" ]
}

# Command implementations
pkgcmd:t:<type>:run() {
    # Run tests
    your-test-command "$@"
}

pkgcmd:pkg-name:<type>:run() {
    # Output package name
    echo "my-package"
}

pkgcmd:pkg-version:<type>:run() {
    # Output package version
    echo "1.0.0"
}
#+end_src

For release workflow integration, create executable scripts in:

- ~<type>/source/check/~ - Pre-test sanity checks
- ~<type>/dist/check/~ - Distribution validation
- ~<type>/release/build/~ - Build distribution files
- ~<type>/release/check/~ - Post-build validation
- ~<type>/release/publish/~ - Publishing commands
- ~<type>/git-hook/<hook>/~ - Git hook checks run by ~pkg-git-hook~
- ~<type>/autogen.d/~ - Scripts copied into projects by ~pkg vendor~
  and sourced by ~./autogen.sh~ (not executed: no shebang, not
  executable; ~return 1~ aborts the step).  Use ~depends_soft~ for
  optional tools.
